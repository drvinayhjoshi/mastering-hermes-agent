# Project status without the Friday scramble

## When to Use
When I ask for project status, the Friday report, or client
updates.

## Procedure
1. For each project in ~/Business/Projects/, read the task list
   and scope.md. Read-only; never edit a task.
2. Count done, open, overdue, blocked. List items waiting on the
   client with the number of days.
3. List tasks with no matching item in scope.md.
4. Apply status-rules.md and state which rule fired.
5. Draft a client update: done, next, needed from them, any date
   at risk. Then one internal summary for me.

## Pitfalls
- Status comes from the written rule, never from tone. Quote the
  rule that fired.
- A new request is not automatically out of scope. Report it as
  "not in scope.md"; whether to charge is my decision.
- Never tell the client a date has slipped unless the schedule
  shows it. Never promise a new date.

## Verification
Tasks counted per project = tasks in the export. Every "not in
scope" item names its source (email, task, call).

## Stop and Ask Me Instead When
- A milestone will be missed and the client has not been told.
  Tell me first, and draft no client update for that project.
- The project is in dispute or the client is unhappy. Write the
  internal summary only; no client draft.
- A change order or extra cost is involved. List what was asked
  for and when; leave charging to me.

## Approval Required
Read-only in the project tool. Client updates come to me as
drafts; never send them. Never send, pay, post or delete
anything without my explicit "approved".
